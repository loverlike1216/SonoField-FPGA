### 本次任务的核心目标

在不破坏旧版本、现有 Git 历史、正式工程决策和已验证功能的前提下，整理 SonoField-FPGA 的工程目录。

最终希望实现：

1. `v5/` 成为 AX7020 平台唯一的正式开发版本目录。
2. 根目录只保留当前开发必须使用的工程入口、版本目录、共享信息池和管理文件。
3. 历史资料、废弃的板卡配置、旧日志及经确认不再被使用的文件，分类归档到 `archive/`。
4. `archive/` 默认冻结，普通开发任务不主动检索、不修改、不参与构建。
5. 根目录继续作为 Git Repository 的工作区，不创建新的正式 Repository。
6. 历史版本、正式决策、测试证据和原始文件不得丢失。
7. 完成后 GitHub 和本地工程状态保持一致。

**最高执行原则：先保证 v5 正常运行，再整理历史文件。绝不能先移动、删除旧文件，然后才尝试修复当前版本。**

### 2.3 先修复 v5 的脚本路径

**只能优先修改复制到 v5 的脚本和配置，不得直接修改冻结旧版本中的原始脚本。**

处理原则：

1. v5 源码必须从 v5 自身读取。
2. v5 脚本必须优先引用 v5 的配置和约束。
3. 通用共享状态可以引用根目录 `shared/`。
4. 不允许正常运行时偷偷加载 v2 的 RTL 或八角板 XDC。
5. 不要用直接写死的绝对路径替代所有引用。
6. 尽量使用相对路径、统一路径配置或脚本自动定位工程根目录。
7. 外部工具安装路径可以保留，但必须明确声明和检测。

例如：

旧方式：

```text
ROOT\v2\rtl\...
ROOT\v2\scripts\...
ROOT\Zynq7020\...
```

新方式：

```text
ROOT\v5\rtl\...
ROOT\v5\scripts\...
ROOT\v5\hardware\ax7020\...
```

对于 AX7020，必须使用经过核验的官方引脚、电压、时钟和 PS 配置，不能简单复制八角板的 XDC 或 PS preset。

### 2.4 建立 v5 Baseline

在移动任何历史文件之前，进行当前环境允许的真实验证：

- Python 单元测试
- RTL 仿真
- Vivado XSim
- 核心模块回归
- 协议及 AXI 离线测试
- 关键脚本启动检查
- Vivado 2025.2 工程加载
- 工程文件完整性检查
- XDC 引用检查
- 综合及适用的布局布线验证

AX7020 实板、外部 PCB 或硬件参数不具备条件时，明确记录 `NOT_RUN`，不得用仿真冒充实测。

新平台约束不齐全时，不允许通过删除约束、降低标准、添加无依据的 false path 等方式伪造 Timing PASS。

需要证明：

**v5 不依赖旧版本的工作目录，也能正确完成其已具备条件的构建与测试。**

生成：

`v5/evidence/BASELINE_VALIDATION.md`

未通过关键验证时，不进入历史目录迁移。

## 六、Stage 4：正式整理历史资料

建立：

```text
archive/
├── README.md
├── legacy_versions/
├── legacy_board/
├── legacy_pcb/
├── historical_evidence/
├── deprecated_designs/
└── manifests/
```

注意：

**archive 只存经审计确认适合归档的文件，不是将所有旧目录直接塞进去。**

### 6.1 历史版本处理

对于 v1、v2、v3 等正式历史版本：

- 保持原始内容和 Hash。
- 保持 Git 历史可追溯。
- 不得改变已冻结源码。
- 不得直接删除历史验证证据。
- 先确认 v5 已复制全部必要依赖。
- 检查历史版本移动后是否影响旧版复现。

如果整体移动历史版本会破坏历史复现或既有路径约定，先保留原位置，并在审计报告中提出后续归档方案，不强行迁移。

对这类高风险移动，先向用户报告影响并等待确认。

### 6.2 旧板卡资料

与八角板、旧 Zynq7020 平台相关的资料，可以在确认 v5 不再直接依赖后归档。

仍有参考价值的原理图、器件说明、接口参数应完整保存。

### 6.3 旧 PCB / BOM

检查：

- PCB 工程
- 原理图
- 网络表
- BOM
- 器件库
- 机械结构
- 控制板接口定义

当前 AX7020 v5 仍需要的资料必须先复制到 v5，再迁移历史文件。

不得因为文件属于旧版本，就认定其器件、电路设计或测试证据没有价值。

### 6.4 临时文件

`.Xil/`、`build/`、`vivado_pid*.str` 等应逐项确认是否仍被运行中的 Vivado、脚本或证据索引使用。

优先通过忽略规则和构建输出隔离来保持整洁，不要为了清理目录强制删除缓存。

`.venv/` 在新环境可正常运行前不要删除。

对于大型日志或二进制生成物，不得未经评估就全部上传 GitHub。

### 6.5 Git 归档

对已经跟踪的文件，优先使用可以保留 Git 可追踪性的移动方式。

归档后生成：

`archive/manifests/MIGRATION_MANIFEST.md`

记录原始路径、目标路径、Hash、迁移原因和恢复办法。

## 七、Stage 5：迁移后完整验证

整理完成后，必须重新验证。

不能只因为 Stage 2 已经测试通过，就认为迁移后也会正常。

重点检查：

1. v5 是否还引用已经移动的历史文件。
2. Vivado 是否能正确打开当前工程。
3. Tcl 脚本是否能正常运行。
4. RTL 文件列表是否完整。
5. Python 模块和导入路径是否正常。
6. 仿真及测试脚本是否正常。
7. AX7020 的 XDC 和 PS 配置是否来自当前版本。
8. GitHub Actions 是否存在失效路径。
9. 当前版本的测试结果是否与迁移前一致。
10. 旧版本文件是否完整且可追溯。

将以下结果进行对比：

```text
BEFORE_MIGRATION
AFTER_MIGRATION
```

重点比较：

- 源码 Hash
- 测试数量
- PASS/FAIL
- 仿真行为
- 固定输入的结果 Hash
- 构建文件完整性
- 实际可执行的 Vivado 验证结果

如果存在回归，暂停归档并恢复到迁移前基线，定位原因后重新验证。

**绝不能通过降低测试数量、跳过失败测试或更改 Acceptance 来使整理后的工程显示 PASS。**
